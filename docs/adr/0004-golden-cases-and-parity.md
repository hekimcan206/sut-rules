# 4. Golden cases per rule, and byte-exact parity with medula-precheck as the adoption contract

- Status: accepted
- Date: 2026-11-12

## Context

A rule language is only adoptable if two questions have mechanical answers: "does this rule do what it says?" and
"does the new engine do what the old one did?". Rule authors will edit files without running a debugger, so the
tests must live next to the rules and be cheap to write.

## Options considered

1. **xUnit tests in C# per rule.** Familiar to developers, invisible to rule authors, and they drift from the files.
2. **Full invoice JSON per case.** Explicit but verbose: a 20-line invoice per case hides the one field that matters.
3. **A base invoice plus a JSON Merge Patch (RFC 7386) per case**, with the exact expected findings, in one file per
   rule; a coverage contract enforced by the test suite.

## Decision

Option 3 for rule-level tests, plus a whole-engine parity test.

- `rules/golden/_base.json` is a clean invoice in every SUT version. `rules/golden/<ID>.json` holds the cases for
  one rule: a name, a merge patch, and the complete list of findings the rule must produce (line, severity,
  expected, actual; optionally code, English reason and fix value). Only the rule under test runs.
- **Coverage contract** (fails the build): every rule has a golden file, at least one passing case where it fires
  and one where it does not, and a firing case in **every version block**, so an amendment that changes a severity
  or parameter cannot ship untested.
- `sut-rules test` runs the same cases from the command line for rule authors; CI runs them through xUnit, one
  theory row per case, so a failure names the rule and case.
- **Parity**: 2,000 invoices generated by medula-precheck v1.0.0 (seed 22, 40% defect rate, invoice dates across all
  three SUT versions) and the report its hand-written engine produced are committed (gzip, about 310 KB). Every invoice
  result from the rule files must match that report **byte for byte** as JSON: outcome, totals, amount at risk, and
  every finding's rule, severity, line, code, expected and actual values, Turkish and English texts and fix. The
  fixture fires all 22 rules (a test checks that too).

## Consequences

- 108 golden cases cover boundaries the parity data hits only by chance: 29 February birthdays, window edges for
  frequency and repeat-examination rules, the 45-day deadline exactly, codes withdrawn by an amendment.
- Parity is evidence for the claim that medula-precheck could adopt this engine without changing a single output.
  It is limited to what that generator produces; the golden cases and the FsCheck properties cover the rest.
- Byte-exact comparison is strict on purpose: an early version of the test compared with `JsonNode.DeepEquals`,
  which treats `120.00` and `120.0` as equal; a report is text, so the comparison is too.
- Mutation checks during development (changing `<=` to `<` in FRQ-001, 45 to 50 in ADM-001) failed the parity and
  golden tests as expected.

- RFC 7386, JSON Merge Patch: https://www.rfc-editor.org/rfc/rfc7386
- medula-precheck v1.0.0: generator, engine and golden-case design (51 hand-written cases).
