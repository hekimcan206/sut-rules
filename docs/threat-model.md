# Threat model

Scope: the rule engine library, the `sut-rules` CLI and the HTTP API, deployed inside a hospital network behind the
billing system (HBYS) gateway. All data in this repository is synthetic.

## Assets

| Asset | Why it matters |
|---|---|
| Invoice data in requests | Special-category health data under KVKK (diagnoses, procedures, age, sex) |
| Rule files and catalog | They decide what gets billed; a wrong rule costs money or passes a claim that SGK will cut |
| Reports | Name invoices and codes; must not widen access to patient identity |
| Availability of the check | Billing deadlines; a hung engine delays a whole period |

## Actors

- **Billing system / clerk**: sends invoices, reads reports. Trusted to send its own data, not trusted to send
  well-formed data.
- **Rule author**: edits rule files through review. Trusted to intend correct rules, not trusted to write them
  without mistakes.
- **Attacker on the internal network**: can reach the API port if it is exposed beyond the gateway.
- **Attacker with write access to the rule directory** (compromised deploy pipeline, mis-set volume permissions).

## Threats and mitigations (STRIDE)

| # | Threat | Mitigation | Residual risk |
|---|---|---|---|
| S1 | Spoofed caller submits invoices or reads rules | None in the service: it has no authentication and is meant to sit behind the HBYS gateway, which authenticates. The compose file binds to 127.0.0.1. | Exposing the port directly is a deployment error; documented in README and SECURITY. |
| T1 | A rule file is edited to pass invoices that should be rejected | Rules are code-reviewed files with golden cases; the coverage contract fails CI when a rule or a version block has no firing case; every report carries the bundle SHA-256 and `GET /api/v1/rules/{id}` returns the source, so an audit can prove which rules ran. | Someone with write access to the mounted directory can still change behaviour after review; mount it read-only (compose does) and deploy rules from the reviewed repository only. |
| T2 | A half-written or broken rule file takes effect | Bundles load all-or-nothing; a rejected reload keeps the last good bundle, logs every diagnostic, and turns readiness to Degraded. A broken bundle at startup stops the process. | None known. |
| R1 | "Which rules judged this invoice?" cannot be answered later | Bundle hash in every report body and in the `X-Rule-Bundle` header; structured logs record each load with its hash. | Reports are not stored by the service; the caller must keep them. |
| I1 | Patient identity leaks through reports or logs | The model has no name or national-id field (a patient is an opaque token); unknown JSON fields such as a name are ignored on input and never echoed; reports carry invoice numbers and codes only; request logging records method, path, status and duration, never bodies. | Diagnoses and procedures are in the request and response by necessity; protect transport (TLS at the gateway). |
| I2 | Error details reveal internals | RFC 9457 problem details with a trace id; health endpoints return status and durations only. | - |
| D1 | A rule (or a malicious edit) hangs the engine | The language is total: no recursion, no unbounded loops, comprehensions iterate finite lists; regular expressions run on the non-backtracking engine (linear time) with a 100 ms timeout; integer overflow raises a run-time error that names the rule. | Quadratic rules on invoices with thousands of lines would be slow, not unbounded. |
| D2 | Oversized requests exhaust memory | Kestrel body limit 8 MB; at most 5,000 invoices per request (configurable); larger batches belong in the CLI. | No rate limiting in the service; the gateway should provide it. |
| E1 | Container escape or privilege use | Chiseled .NET image without shell or package manager, non-root user (UID 1654), read-only root filesystem with a tmpfs for /tmp in compose; CodeQL and a vulnerable-package audit in CI. | - |

## KVKK notes

- Data minimisation (art. 4): the engine reads birth date, sex, diagnoses and services only.
- The service stores nothing: no database, no files written except logs to stdout.
- Test data, golden cases and the parity fixture are synthetic (generated by medula-precheck's Bogus-based generator
  with the Turkish locale, or written by hand).
